# 0006. Use SQLAlchemy Core transactions and Alembic migrations

- **Status:** Accepted
- **Date:** 2026-11-28
- **Decision note:** [Storage options and trade-offs](../../brain/areas/decision-storage.md)
- **Requirements:** DC-5, SC-5, SL-2, QM-4

## Context

The [data model](../design/data-model.md) places quota, identity and playlist state in shared storage. A request handled by a second server instance must see the first instance's committed reservation, refresh or draft claim. The [SRS](../srs.md) requires pooled Neon PostgreSQL in production and permits SQLite for explicit local development.

## Decision

**Backend selection.** Bootstrap selects the backend before serving requests. Production requires an explicitly configured Neon PostgreSQL pooled connection with TLS verification. A missing or invalid configuration, unavailable database or incompatible Alembic revision fails readiness and blocks service. If storage fails mid-request, stop the workflow and preserve any committed intent for recovery. Never switch backends on error. Developers may select a file-backed SQLite database explicitly for local work, or use PostgreSQL for parity.

**Access.** Implement storage ports in the adapter with SQLAlchemy Core and Psycopg 3 for PostgreSQL. Use the async PostgreSQL driver interface on the request path. Bind every runtime value, including the verified owner and expected version, using Core expressions or named bind parameters. Select identifiers and sort expressions from fixed schema definitions. Validate input at the boundary. Keep connection strings, tokens and bound personal values out of logs.

**Atomic operations.** Use a database transaction per storage operation. PostgreSQL uses row locks for multi-row invariants and conditional writes with an affected-row or returned-row check for single-winner claims. For local SQLite enable foreign keys on every connection and acquire the write transaction up front with `BEGIN IMMEDIATE` for read-check-write operations. A busy database may fail the operation; it must never bypass the checks.

| Operation in the data model | Commit boundary and behaviour under contention |
|---|---|
| Reserve and settle quota | Create missing day/layer rows under their unique keys. Lock global before caller, check both units and search calls, then insert the unique attempt and its lines and increase outstanding amounts in the same transaction. A duplicate attempt returns its recorded result. Before dispatch, commit a successful reservation. Settle once under the same locks, moving outstanding to charged and releasing unused capacity. Preserve uncertain charges across crashes and reserve remaining calls against the new day at reset. |
| Confirm and resume drafts | After session, CSRF and origin checks, claim by owner, expected state, version and expiry. Only a returned row authorizes progress. Commit intent before each external write; record its result before advancing. An ambiguous write becomes uncertain. Only a known partial result can resume after fresh browser confirmation. |
| Consume sign-in state and rotate credentials | Atomically consume the live, browser-bound callback state. Exchange a verified, unexpired MCP code and insert its family in one transaction. For refresh, lock the family, recheck the digest, consume it and issue the successor pair together. Commit family revocation on replay before returning the error. Serialize Google refresh per account with a durable exclusive claim and version-checked completion; an ambiguous upstream rotation requires reconciliation or reauthorization. |
| Admit personal data, disconnect and clean up | Lock the account before admitting cache or draft bytes or changing personal state. Recheck ownership, account availability and the size cap under that lock. Disconnect disables access first, settles outstanding reservations under the quota lock order, then deletes personal rows while retaining anonymous totals. All paths taking both account and budget locks acquire account first, then global and caller budgets. |
| Enforce a rate window | Use a unique caller/window key and conditional upsert that increments only below the limit. Return the retry delay when the increment fails. |

Keep network calls outside database transactions. Retry a rolled-back database-only operation as a unit. After a lost commit acknowledgement, look up the durable attempt or intent before proceeding. Repeating a transaction must never trigger a second playlist write.

**Migrations.** Use versioned Alembic revisions for both dialects. A single deployment migration job runs against a direct PostgreSQL connection before new instances become ready. Request workers use the pooled endpoint and check revision compatibility. Review autogenerated diffs, constraints and backfills. For rolling releases, add compatible structures first, migrate data, and remove old structures only after old workers are drained. Abort deployment on an upgrade failure.

## Consequences

Pure domain and service tests can use injected fakes. Exercise local startup and schema upgrades on explicit SQLite. Use disposable PostgreSQL with independent connections for quota contention, refresh replay, double confirmation, disconnect races and migration upgrades with existing data. Verify that production startup rejects SQLite and that losing PostgreSQL never creates a local database. Runtime dependencies, migration files and these integration tests belong to implementation work.
